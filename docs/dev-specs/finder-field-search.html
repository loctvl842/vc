Finder field search - dev spec

A pure tokeniser splits cwd:jarvix title:nvim startup into field terms and a remainder. The matcher narrows by each field term, then scores the remainder exactly as today. The prompt colours recognised prefixes. Queries without a field term are untouched.

PM spec: docs/pm-specs/finder-field-search.md

How it flows

Solid arrows: the query. Dashed: prompt colouring, done on every keystroke without the debounce.

Research: reuse and build

Reuse: the matcher's term parser and score_text, the existing field spans, the prompt extmarks. Build: one tokeniser module and one highlight group.

Where this differs from the PM spec text - please read
  • Quoted phrase must be an exact substring. title matches loosely, so title:"fix login" run through the fuzzy parser would match "Fix flaky login test" (letters in order). Scenario 8 requires it not to match, so a quoted value becomes one exact term whose text keeps its spaces. A new matcher.term() builds a term directly instead of going through whitespace splitting.
  • Operators leak into field values. An unquoted value goes through the same term parser as a normal word, so cwd:^jar, cwd:a|b and cwd:!work behave like their normal-search forms. This is deliberate reuse, not a promised feature: negation stays out of scope in the PM spec and gets no tests or docs.
  • Several normal words still must all match inside one field (score_item today). Field terms narrow before that and do not change it.
  • Subset elimination breaks for typing cwd then cwd: then cwd:j (the word cwd was a plain word, then stopped being one), so it is limited to queries with no field terms (Phase 1).
  • PM spec State 5 mock showed an invented "(no sessions)" text; it now shows today's No sessions match "<text>".

Phases

Each phase merges on its own. Phase 1 is the whole narrowing for four fields.

Phase 1: Narrow by field - cwd:, title:, recap:, msg: end to end in the matcher

StepActionWhy
Tokeniser
lua/vc/finder/fieldquery.lua		parse(text) scans the text. A term is a whitespace-delimited token name:value where name is one of cwd title branch pr recap msg (lowercase, directly followed by :) at the start of the token. Value is the rest of the token; if it starts with ", the value runs to the next " (or the end of the text when unterminated) and quoted = true. Returns terms = {{name, value, quoted}} only for non-empty values, rest = the text with every recognised term (empty-valued ones too) removed and spaces collapsed, and spans = {{s, e}} of each recognised name: prefix (empty values included) for colouring. Unknown names stay in rest.single, testable place for the syntax; pure so it needs no UI.
Depends: None · Risk: Low
Filter state
lua/vc/finder/filter.lua		add text and terms; update(text) sets text, calls fieldquery.parse, sets terms and pattern = rest. new() initialises all three.pattern keeps meaning "what the matcher scores"; text is "what the user typed".
Depends: Step 1 · Risk: Low
Callers read the typed text
lua/vc/finder/init.lua, lua/vc/finder/keymaps.lua, lua/vc/finder/render.lua		init.lua (_sync_items, set_rows) uses filter.text == "" for "New session" (a query of field terms only must remove it: its empty text matches nothing, so it would otherwise survive a score of 1). keymaps.lua:39 compares the input text with filter.text. render.lua builds the empty message from filter.text.otherwise cwd:j alone would keep "New session", Enter-while-typing would never see the text as current, and the message would show only the remainder.
Depends: Step 2 · Risk: Medium (easy to miss a reader; grep filter.pattern after)
Name the spans
lua/vc/finder/source.lua		in items, give each field span a name: title, cwd, recap, msg.field terms look spans up by name.
Depends: None · Risk: Low
Matcher
lua/vc/finder/matcher.lua		field narrowing reuses the existing matching, and the ranking comes from the remainder only (field scores are not added).
Depends: Steps 2, 4 · Risk: Medium (hot path; subset logic; keep the no-field path byte-identical)
Tests
test/finder/fieldquery_spec.lua, test/finder/finder_spec.lua		tokeniser cases (below); finder cases: cwd: narrows by folder only, field plus remainder, term order irrelevant, two terms for one field, cwd: alone changes nothing, ticket:42 is plain text, title:"fix login" exactness, loose vs plain per field, case sensitivity, "New session" gone for a field-only query, the typing sequence cwd, cwd:, cwd:j giving the right list at each step.PM scenarios 1 to 10 become executable.

Testing

  • Headless tests: make test (all); make test SPEC=test/finder/fieldquery_spec.lua and SPEC=test/finder/finder_spec.lua per phase. make lint (stylua) before each commit.
  • Bench: scripts/bench-index.lua is not affected (no index change). Run a quick 5 000-row timing of a plain query and of cwd:x y through matcher.run to confirm the no-field path is unchanged and the field path is not slower than a normal query; no new bench file.
  • Manual: open NVIM_APPNAME=VimClaude nvim and walk the PM spec scenarios: 1 (narrow by folder then title), 2 (term order), 3 (same word with and without a field), 4 (same field twice), 5 (no match: counter 0 / N, message No sessions match "..."), 6 (type cwd: letter by letter and watch the prefix colour and the list), 7 (ticket:42, a URL), 8 (quoted phrase), 9 (title:nvm vs msg:nvm), 10 (capital letter). Check the prefix colour in a light and a dark terminal, and highlights inside folder, recap, message, branch and PR on a narrow list (34 columns).
