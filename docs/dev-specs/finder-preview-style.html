Preview style: dev spec

Turn the preview from plain transcript text into a styled document: clean lines with no markdown markers, highlight marks, and folds. Records become typed blocks; four small renderers (markdown, code, tool line, diff) turn blocks into lines and marks; the preview applies marks as extmarks and lets Neovim wrap with a hanging indent.

Review copy of docs/dev-specs/finder-preview-style.md (the .md wins). PM spec: docs/pm-specs/finder-preview-style.md.

How it works

Green outline = new module. The render stage is chunked and cancellable like the feed stage today, so a huge session never blocks typing.

Research

Searched: transcript, render_file, set_content, line_hl_group, foldexpr, treesitter in lua/ test/ scripts/.

Found: Builder chunking + cancel, fold map plumbing, palette helpers, fixtures, preview cache. No markdown, code highlight or diff code; no treesitter use yet.

Checked built-ins (nvim 0.12.6): bundled markdown, markdown_inline, lua, vim, c parsers; get_string_parser; breakindent with list:-1. Real transcripts carry toolUseResult.structuredPatch with line numbers for edits.

Decision: Use tree-sitter (markdown, code) with plain fallback, Use structuredPatch for diffs, Reuse Builder/fold/highlight plumbing, Build block model and the four renderers.

Phases

Each phase is mergeable on its own and leaves the preview working.

Phase 1 - Message layout and tool lines

Goal: the Claude Code skeleton with plain text inside. > prompts, ● replies, ● Name(args) + ⎿ results, thinking folded. Replaces ## You headings and the one-fold-per-run model.

  • Block model with results paired to calls (transcript.lua) Medium
  • Render stage, truncate results to N lines, rest folded as … +N lines (transcript.lua) Medium
  • Tool line summaries (toolline.lua) Low
  • Preview applies marks and the new folds (preview.lua) Low
  • Phase-1 highlight groups (highlights.lua) Low
  • Rewrite transcript and preview tests, add toolUseResult fixtures Low

Phase 2 - Markdown in replies

Goal: no raw markers, real bold / italic / headings / lists / quotes / links. Depends on Phase 1.

  • Markdown renderer on tree-sitter, one pass builds text and marks (markdown.lua) High (offset bookkeeping)
  • Wire prompts and replies through it (transcript.lua) Medium
  • Hanging indent via breakindent + list:-1 (preview.lua) Medium
  • Markdown groups (highlights.lua) Low
  • Table tests per construct (test/markdown_spec.lua) Low

Phase 3 - Code blocks

Goal: highlighted fences using our palette, never the colorscheme. Depends on Phase 2 step 1.

  • Highlight query to palette groups, aliases, pcall on missing parser (code.lua) Medium
  • Fence rendering: dim language label, indent, syntax marks (markdown.lua) Low
  • Code groups (highlights.lua); red, green, yellow, blue, cyan slots already exist, add magenta (ANSI 5) Low
  • Tests (test/code_spec.lua) Low

Phase 4 - Diffs

Goal: Update / Write as colored diffs with line numbers, straight from structuredPatch. Depends on Phase 1.

  • Diff lines + count line, fallback when no patch (toolline.lua) Medium
  • Diff bands with BeastVim's tints (line bg = 15% of green / red over the terminal bg, sign fg 60%, bold) built from the terminal palette (highlights.lua) Low
  • Tests with sample patches (test/toolline_spec.lua) Low

Phase 5 - Edge content and performance

Goal: tables, images, nothing dropped, long sessions stay responsive.

  • Pipe tables with box lines (markdown.lua) Medium
  • Placeholders and plain fallback for unknown content Low
  • Chunked cancellable render, early first screen, bench script Medium
  • Every new group defined in rgb and cterm modes, redefined on background flip (highlights_spec.lua) Low

Decisions for you

1. Wrapping
  • Recommended: native wrap with breakindent. Re-flows on resize, copied paragraphs stay whole. Fallback to pre-wrapping only if list indents come out wrong in Phase 2 step 3.
  • Pre-wrap at render time: exact control, but re-render on resize and hard line breaks in copied text.
2. Markdown parsing
  • Recommended: tree-sitter (bundled, handles nesting). Missing parser means plain text, never an error.
  • Hand-written scanner: no dependency, more edge-case bugs.
3. Constants (result lines shown, truncation lengths, band tint): start with guesses, fix them when your screenshots arrive. They live only in highlights.lua and config.lua.

Testing

  • Headless: make test, make lint; each phase adds its own spec; Phase 1 rewrites the preview and transcript specs.
  • Bench: scripts/bench-preview.lua after Phase 5 (5000-message session).
  • Manual: PM scenarios 1-8 in dark and light terminal themes, compared against your Claude Code screenshots.

Success criteria

  • Preview and Claude Code read as the same screen
  • No raw markdown symbols in any reply
  • Distinct bold, italic, headings, lists, quotes, inline code, links, strikethrough
  • Highlighted code for common languages; unknown language still looks like code
  • One line per tool call, results expand in place; colored diffs with line numbers
  • Light and dark readable, live repaint on flip
  • Rapid selection never freezes typing; hanging indents stay straight
  • make test and make lint pass; every new group has a cterm fallback
